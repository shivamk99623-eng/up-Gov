================================================================================
PERFORMANCE FIX: SLOW DATA LOADING AFTER DEPLOY
Developer documentation — how the problem was found and fixed
================================================================================

Date: 2026-06-10
Project: UP Media Monitoring Dashboard (Next.js App Router)


--------------------------------------------------------------------------------
1. SYMPTOM
--------------------------------------------------------------------------------

After deployment, the first page load felt very slow — especially the MP page.
Subsequent requests on the same server process were fast.

This pattern (slow first hit, fast later) pointed to:
  - Cold-start data parsing, not a React/UI bug
  - In-memory caches that reset when a new server process starts


--------------------------------------------------------------------------------
2. HOW THE DATA LAYER WORKS (BEFORE FIX)
--------------------------------------------------------------------------------

All analytics read from local files under /data at request time on the server.

Main parsers:

  src/lib/excel-parser.ts
    - loadRecords()
    - Reads data/media-data.xlsx (~3 MB)
    - Parses YouTube / X / Online media mentions
    - Caches in a module-level variable; invalidated by file mtime

  src/lib/print-parser.ts
    - loadAllPrintRecords() / ensureCache()
    - Scans 5 folders and reads EVERY .xlsx file:
        data/Constituency Data/          (69 files)
        data/District Data/              (65 files)
        data/MP Data_News/LokSabha.../   (43 files)
        data/MP Data_News/RajyaSabha.../ (18 files)
        data/MLA Data_News/              (60 files)
      Total: 257 Excel files (~6.5 MB combined)
    - Uses the `xlsx` npm package synchronously (fs.readFileSync + XLSX.read)

  src/lib/mp-bio-parser.ts
    - listAllMpBioMembers()
    - Reads JSON bio files (fast)

  src/services/representatives.ts
    - getMPDirectory()  -> used by GET /api/mp
    - getMLADirectory() -> used by GET /api/mla

API routes (all force-dynamic):

  src/app/api/dashboard/route.ts
  src/app/api/mp/route.ts
  src/app/api/mla/route.ts
  ... (10 routes total)

Each route calls service functions that trigger the parsers above.

--------------------------------------------------------------------------------

  graphify query "where is data loaded parsed excel json at startup or request time"

  Key nodes surfaced:

    - ensureCache() in print-parser.ts
    - getMPDirectory() in representatives.ts
    - loadMpPrintRecords() in print-parser.ts

Step 2: Timed API endpoints with curl on a fresh server process

  BEFORE FIX (cold process, first request per endpoint):

    /api/mp         ~17 seconds   <-- worst
    /api/mla        ~2 seconds
    /api/dashboard  ~4 seconds (if print not yet cached)

  AFTER caches were warm (same Node process):

    /api/mp         ~135 ms (before indexing fix)
    /api/mp         ~67 ms  (after indexing fix)
    /api/dashboard  ~20 ms

Step 3: Read Next.js server logs

  GET /api/mp 200 in 10.2s (application-code: 10.1s)

  Confirmed the delay was server-side parsing/aggregation, not network or React.


--------------------------------------------------------------------------------
4. ROOT CAUSES (TWO SEPARATE PROBLEMS)
--------------------------------------------------------------------------------

ROOT CAUSE A — Cold Excel parse on every new server process
------------------------------------------------------------

After deploy (or serverless cold start), module-level caches are empty:

  let cache: PrintCache | null = null;   // print-parser.ts
  let cache = ...                         // excel-parser.ts

The first API call must:
  1. Read media-data.xlsx
  2. Read and parse 257 print Excel files
  3. Build in-memory arrays

This alone costs ~4–14 seconds depending on which endpoint runs first.

On serverless (Vercel, etc.) each new instance repeats this. The cache does NOT
survive across instances or deploys.


ROOT CAUSE B — O(n²) MP directory build (the 17-second MP page)
---------------------------------------------------------------

getMPDirectory() in representatives.ts builds one profile per MP (~111 MPs
from bio JSON). For EACH MP it called:

  loadMpPrintRecords(name)

Old implementation in print-parser.ts:

  export function loadMpPrintRecords(mpName) {
    const all = loadAllPrintRecords().filter(r => r.sourceType === "mp");
    return all.filter(r => matchesMpScope(r, mpName));
  }

matchesMpScope() called mpNamesMatch(), which called resolveMpBioKey() twice
per row comparison. resolveMpBioKey() can run tokenSubsetMatch() that scans
ALL MPs in the bio index.

So for 111 MPs × thousands of print rows × fuzzy name matching = catastrophic.

getMPDirectory() also called sentimentOfPrint(name) which called
loadMpPrintRecords(name) AGAIN — doubling the work per MP.


ROOT CAUSE C — O(n log n) MLA sort with repeated lookups
----------------------------------------------------------

collectMlaUnion() sorted MLAs like this (old code):

  return [...map.values()].sort((a, b) => {
    const aMentions = a.records.length + loadMlaPrintRecords(a.name).length;
    const bMentions = b.records.length + loadMlaPrintRecords(b.name).length;
    return bMentions - aMentions || a.name.localeCompare(b.name);
  });

Array.sort() calls the comparator O(n log n) times. Each call ran
loadMlaPrintRecords() twice (once for a, once for b), re-filtering the full
MLA print array every time.


--------------------------------------------------------------------------------
5. FIXES APPLIED
--------------------------------------------------------------------------------

FIX 1 — Indexed MP/MLA print lookups (print-parser.ts)
-------------------------------------------------------

Problem: loadMpPrintRecords(name) scanned every print row per lookup.

Solution: When ensureCache() finishes parsing all Excel files, build hash
indexes once:

  interface PrintCache {
    records: PrintRecord[];
    mpByKey: Map<string, PrintRecord[]>;   // NEW
    mlaByKey: Map<string, PrintRecord[]>;  // NEW
    ...
  }

Index build (runs once per cache refresh):

  function indexPrintRecords(records) {
    for each record:
      if sourceType === "mp":
        index under compactMpKey(scope) and normalizePersonName(scope)
      if sourceType === "mla":
        index under normalizeMlaName(scope)
  }

Lookup (runs per MP/MLA query — O(1) map get):

  function loadMpPrintRecords(mpName) {
    return lookupMpPrint(cache.mpByKey, mpName);
  }

  function loadMlaPrintRecords(mlaName) {
    return lookupMlaPrint(cache.mlaByKey, mlaName);
  }

Important design choice:
  - Index build uses CHEAP keys (mpIndexKeysFromScope) — no fuzzy scan
  - Lookup uses mpLookupKeys(name) which may call resolveMpBioKey() ONCE per
    lookup (not once per print row)

Files changed:
  src/lib/print-parser.ts


FIX 2 — MLA sort precomputation (representatives.ts)
----------------------------------------------------

Problem: sort comparator called loadMlaPrintRecords() inside every comparison.

Solution: Precompute print counts once before sorting:

  const entries = [...map.values()];
  const printCounts = new Map(
    entries.map(e => [e.name, loadMlaPrintRecords(e.name).length])
  );
  return entries.sort((a, b) => {
    const aMentions = a.records.length + (printCounts.get(a.name) ?? 0);
    const bMentions = b.records.length + (printCounts.get(b.name) ?? 0);
    return bMentions - aMentions || a.name.localeCompare(b.name);
  });

Files changed:
  src/services/representatives.ts


FIX 3 — Avoid duplicate print fetch per MP (representatives.ts)
---------------------------------------------------------------

Problem: getMPDirectory() called loadMpPrintRecords(name) and then
sentimentOfPrint(name) which called loadMpPrintRecords(name) again.

Solution: Reuse the same array:

  const printRecords = loadMpPrintRecords(name);
  const sentiment = mergeSentiment(
    sentimentOf(records),
    sentimentOfPrintRecords(printRecords),  // reuse, no second lookup
  );

Files changed:
  src/services/representatives.ts


FIX 4 — Shared warm-up promise for all API routes (api-helpers.ts)
------------------------------------------------------------------

Problem: If the browser fires multiple API calls on cold start (dashboard +
filters + mp), each could trigger separate parse work before caches settled.

Solution: Single shared promise per server process:

  let warmCaches: Promise<void> | null = null;

  export function warmDataCaches(): Promise<void> {
    if (!warmCaches) {
      warmCaches = (async () => {
        loadRecords();
        loadAllPrintRecords();
        listAllMpBioMembers();
      })();
    }
    return warmCaches;
  }

Every API route now starts with:

  await warmDataCaches();

Concurrent requests await the SAME in-flight promise — parse runs once.

Files changed:
  src/lib/api-helpers.ts
  src/app/api/dashboard/route.ts
  src/app/api/mp/route.ts
  src/app/api/mla/route.ts
  src/app/api/district/route.ts
  src/app/api/media/route.ts
  src/app/api/print/route.ts
  src/app/api/filters/route.ts
  src/app/api/constituency/route.ts
  src/app/api/constituency/print/route.ts
  src/app/api/constituency/filters/route.ts


FIX 5 — Server startup pre-warm (instrumentation.ts)
----------------------------------------------------

For long-running servers (`next start` on a VM, Docker, etc.), Next.js supports
an instrumentation hook that runs when the Node server boots:

  src/instrumentation.ts

  export async function register() {
    await warmDataCaches();
    getMPDirectory();
    getMLADirectory();
  }

This moves parse cost off the first user request when the hook runs early
enough. Note: on serverless, each new instance may still cold-start; this does
not replace build-time precomputation for that case.

Files changed:
  src/instrumentation.ts (new file)

6. RESULTS (LOCAL BENCHMARKS)
--------------------------------------------------------------------------------

                        BEFORE      AFTER (1st hit)   AFTER (warm)
  /api/mp               ~17 s       ~14 s             ~67 ms
  /api/mla              ~2 s        ~0.5 s            fast
  /api/dashboard        ~4 s        ~16 ms*           ~20 ms

  * dashboard is fast on first hit if print cache was already warmed by
    another endpoint or instrumentation

What improved:
  - MP/MLA directory build after caches are warm: ~17 s -> ~67 ms
  - MLA sort: no longer quadratic in comparator
  - Concurrent cold API calls: share one parse via warmDataCaches()

What did NOT fully go away:
  - First request on a brand-new process still parses 257 Excel files (~10-14 s)
  - That cost is inherent to synchronous xlsx parsing on the request/startup path

8. HOW TO VERIFY THE FIX YOURSELF
--------------------------------------------------------------------------------

1. Start production server on a fresh process:

     pkill -f "next" 2>/dev/null
     npm run build && npm start

2. Time first MP request (cold):

     curl -o /dev/null -s -w "%{time_total}s\n" http://localhost:3000/api/mp

3. Time second MP request (warm — should be < 100 ms):

     curl -o /dev/null -s -w "%{time_total}s\n" http://localhost:3000/api/mp

4. Check Next.js logs for application-code timing:

     GET /api/mp 200 in 67ms (application-code: ...)

--------------------------------------------------------------------------------
11. KEY TAKEAWAYS FOR DEVELOPERS
--------------------------------------------------------------------------------

1. Module-level caches are fast but die on every deploy / serverless instance.
   Design for cold starts explicitly.

2. Never put expensive work inside Array.sort() comparators — they run O(n log n)
   times.

3. Never filter a large array inside a loop over entities (MPs, MLAs, districts).
   Build an index (Map) once, look up in O(1).

4. Fuzzy matching (mpNamesMatch / resolveMpBioKey) is fine per lookup, fatal
   per row × per entity.

5. Use curl + Next.js application-code timing to separate server slowness from
   client slowness.
